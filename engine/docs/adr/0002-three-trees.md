# ADR-0002: Три дерева — Widget → Element → RenderObject

- Статус: принято
- Дата: 2026-11-17

## Контекст

Нужна модель, по которой код приложения превращается в картинку и обновляется при изменении данных.

## Решение

Модель Flutter:

- **Widget** — неизменяемое описание («конфигурация»). Дешёвое, создаётся заново при каждом build.
- **Element** — экземпляр виджета в дереве. Живёт долго, держит `State`, решает: обновить существующее
  поддерево или пересоздать (тот же тип + тот же ключ → обновить).
- **RenderObject** — геометрия: лэйаут, отрисовка, hit-test. Дорогой, живёт долго, есть только
  у `RenderObjectWidget`.

## Альтернативы

| Модель | Примеры | Плюсы | Минусы |
|---|---|---|---|
| Immediate mode | Gio, Dear ImGui | очень просто, нет дерева | состояние и анимации на пользователе; лэйаут каждый кадр |
| Реактивные сигналы | SolidJS, Compose | точечные обновления без diff | сложный рантайм, «магия» отслеживания зависимостей |
| Retained + ручные мутации | Fyne, классические тулкиты | просто и понятно | нет декларативности, легко рассинхронизировать UI и данные |
| **Три дерева** | Flutter | декларативно, предсказуемо, хорошо изучено | три иерархии типов, reconciliation, аллокации на build |

## Последствия

- Разделены ответственности: конфигурация (Widget), жизненный цикл (Element), геометрия (RenderObject).
- Огромный объём готовых знаний: исходники Flutter читаются как учебник.
- Каждый build аллоцирует новые виджеты — Go GC с этим справится, но аллокации на кадр меряем бенчмарками.
- Сложная часть — `updateChildren` с ключами: одна из главных учебных задач M4.
