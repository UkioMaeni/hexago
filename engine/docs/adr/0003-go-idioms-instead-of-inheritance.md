# ADR-0003: Go-идиомы вместо наследования; API виджетов

- Статус: принято, открытые вопросы решаем экспериментом на M4
- Дата: 2026-11-17

## Контекст

Flutter построен на классах: `RenderBox` переопределяет `performLayout`, базовый `layout()` его вызывает.
В Go встраивание (embedding) — не наследование: метод встроенной структуры **не видит** методов внешней.
Если `Box.Layout()` вызовет `b.PerformLayout()`, вызовется метод самой `Box`, а не твоего `RenderFlex`.

## Решение

1. **Данные — в базе, алгоритм — в функции пакета.** Общие поля (`parent`, `size`, флаги) лежат во встроенной
   структуре (`rendering.Box`, `widgets.elementBase`). Общие алгоритмы — функции пакета, принимающие
   интерфейс: `rendering.Layout(r RenderBox, c, parentUsesSize)`. Функция достаёт данные через
   неэкспортируемый метод `r.box()` и вызывает «виртуальный» `r.PerformLayout(c)`.
2. **Неэкспортируемый метод как печать.** Интерфейс `widgets.Widget` содержит неэкспортируемый метод.
   Реализовать его можно только встроив одну из баз: `widgets.Stateless`, `widgets.Stateful`,
   `widgets.Inherited`, базы для RenderObject-виджетов. Забыл встроить — ошибка компиляции.
   Вид виджета определяется по встроенной базе, без рефлексии.
3. **Виджеты — указатели на struct-литералы.** `&widgets.Padding{Padding: painting.All(8), Child: …}`.
   После создания виджет не меняют (конвенция; позже линтер). Тот же указатель, что в прошлом build
   → поддерево не перестраивается (аналог `const`-виджетов Flutter).
4. **`canUpdate` = одинаковый `reflect.Type` + одинаковый ключ.** `reflect.TypeOf` на интерфейсе — это
   чтение указателя на тип, а не обход полей; в горячем пути допустимо.
5. **Дженерики — точечно:** `StateBase[W]` (типизированный `Widget()` без приведений),
   `DependOn[T](ctx)` для InheritedWidget, `Tween[T]`, `ValueNotifier[T]`. Где хватает интерфейса — интерфейс.
6. **Обработчики — func-поля:** `OnTap func()`. `nil` — обработчика нет (кнопка неактивна).
7. **Ошибки.** Ошибка разработчика (нарушен протокол лэйаута, `SetState` после `Dispose`) — `panic`
   с понятным текстом и путём в дереве. Ошибка окружения (нет шрифта, не создалось окно) — `error`.

## Открытые вопросы (решим на M4, попробовав в коде)

- **Ключи.** В Go нельзя задать поле встроенной структуры прямо в литерале внешней. Варианты:
  - поле `Key` в базе: `&Item{Stateless: widgets.Stateless{Key: k}, Title: t}` — честно, но многословно;
  - обёртка: `widgets.Keyed(k, &Item{Title: t})` — коротко, но ключ у обёртки, а не у элемента `Item`
    (важно для `GlobalKey` → `State`);
  - своё поле `Key` + метод `WidgetKey()` в каждом виджете, которому нужен ключ.
- **Проверка вида.** Встроил `widgets.Stateless`, но забыл `Build` — ловить при компиляции конвенцией
  `var _ widgets.StatelessWidget = (*Item)(nil)` или паникой при монтировании?
- **Имя контекста:** `BuildContext` (как во Flutter) или `Context` (короче, но путается с `context.Context`).

## Альтернативы

- Эмуляция классов: база хранит ссылку на «внешний» объект (`ExtendBaseWidget(self)` в Fyne).
  Работает, но легко забыть вызов, и это не Go-стиль.
- Кодогенерация методов для каждого виджета: мощно, но прячет механику — плохо для обучения.

## Последствия

- Код фреймворка читается как Go, а не как Dart в Go-синтаксисе.
- Правило «алгоритм в функции пакета» надо соблюдать везде, иначе всплывут тонкие баги с «невызванным
  переопределением». Ревью проверяет это в первую очередь.
