# ADR-0005: Потоки и раннеры; однопоточный framework

- Статус: принято
- Дата: 2026-11-17

## Контекст

- macOS/iOS требуют, чтобы UI ОС работал на главном потоке процесса; в Windows окно должен обслуживать
  поток, который его создал.
- GPU-контексты (GL, отчасти D3D) привязаны к потоку ОС, а горутины по потокам «гуляют».
- В браузере (wasm) поток один.
- Горутины соблазняют менять дерево виджетов откуда угодно — это гонки данных.

## Решение

1. Три роли — **platform**, **ui**, **raster**. Каждая — «раннер» с интерфейсом `Post(func())`.
2. Десктоп: platform = главный поток ОС (`runtime.LockOSThread()` в `init` пакета `app`),
   ui = своя горутина, raster = горутина с `LockOSThread`.
3. Web и тесты: все три раннера — один поток / одна горутина. Логика shell от этого не меняется.
4. Framework однопоточный: всё дерево живёт на UI-раннере. Из других горутин — только `app.Post(fn)`.
5. Передача кадра: UI отдаёт `*layer.Scene` в канал ёмкостью 1. Сцена после передачи неизменяема
   (`DisplayList` переиспользуется между кадрами, но тоже не меняется) — мьютексы не нужны.
6. Debug-сборка (тег `gexagodebug`) проверяет, что мутации дерева идут с UI-горутины.

## Альтернативы

- Всё на одном потоке везде: проще, но долгая растеризация блокирует обработку ввода.
- Мьютексы вокруг дерева: гонки, дедлоки, непредсказуемые паузы. Flutter тоже однопоточен на UI.

## Последствия

- Тяжёлую работу пользователь выносит в горутины и возвращает результат через `Post` —
  это нужно объяснить в документации и поддержать удобными виджетами (аналог `FutureBuilder`/`StreamBuilder`
  на каналах).
- Однопоточный режим в тестах даёт полностью детерминированные кадры.
