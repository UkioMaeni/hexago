# ADR-0015: hexago пересобирает себя, когда меняются его исходники

- Статус: принято
- Дата: 2026-11-18

## Контекст

- `hexago` ставится один раз: `go install .` в папке `engine`. Движок при этом меняется постоянно.
- Устаревший `hexago` в PATH молча не знает новых команд. Так и случилось: расширение VS Code взяло
  `hexago` из PATH, собранный до появления `hexago devices`, и показало «Нет устройств и эмуляторов»
  вместо ошибки.
- Flutter решает это так же: скрипт `bin/flutter` пересобирает `flutter_tools`, если исходники новее сборки.

## Решение

1. При каждом запуске `hexago` сравнивает время изменения своего файла с исходниками утилиты в движке:
   `main.go`, `go.mod`, `go.sum` и `tools/` (вместе со встроенными шаблонами; без `tools/vscode`).
   Сам движок (`ui/`, `platform/`) в утилиту не входит и пересборку не вызывает.
2. Если исходники новее — `go build` в папке движка рядом с программой, подмена файла и перезапуск
   с теми же аргументами; код выхода передаётся. Запущенный файл Windows переименовать даёт, а удалить нет:
   старая сборка уходит в `hexago.exe.old-<pid>` и удаляется при следующем запуске.
3. Не собралось (в движке ошибка) — сообщение в stderr, и работает прежняя сборка.
4. Перезапущенная сборка себя не проверяет (переменная `HEXAGO_NO_REBUILD`), чтобы не зациклиться.
5. Расширение VS Code показывает в списке устройств настоящую ошибку `hexago`, а не «устройств нет».

## Альтернативы

- Только предупреждать «hexago устарел, выполни go install»: проще, но редактор этого сообщения не покажет,
  а в терминале его легко пропустить.
- Расширение всегда само собирает `hexago` из движка: чинит только VS Code, а не терминал.

## Последствия

- После правки утилиты первый запуск `hexago` дольше на время сборки (обычно секунды благодаря кешу Go).
- Каждый запуск обходит папку `tools/` (десятки файлов) — это миллисекунды.
- Если `hexago` собран не из папки движка (в будущем — готовый дистрибутив), исходников нет и проверка
  ничего не делает.
