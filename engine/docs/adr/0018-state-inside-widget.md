# ADR-0018: Состояние — прямо в структуре виджета; жизненный цикл Init, Update, DependenciesChanged, Dispose

- Статус: принято. Заменяет модель StatefulWidget + State из ADR-0003 (п. о состоянии).
- Дата: 2026-11-18

## Контекст

- Было как во Flutter: виджет с параметрами (`CreateState()`) и отдельная структура состояния
  (`StateOf[Counter]`, `InitState`, `DidUpdateWidget`, `Dispose`). Два типа на один виджет.
- Автор хочет, чтобы состояние подключалось так же, как `Base`, — встраиванием, и жило в той же структуре,
  а методы жизненного цикла назывались своими словами.

## Решение

1. **`widgets.State` встраивается вместо `widgets.Base`.** Такой виджет — виджет с состоянием.
   ```go
   type Counter struct {
       widgets.State
       Title string // с большой буквы — параметр от родителя
       count int    // с маленькой — своё состояние
   }
   ```
2. **Живой экземпляр.** Когда виджет впервые появляется в дереве, элемент создаёт его копию-указатель
   (`*Counter`) и хранит её, пока виджет в дереве. Родитель пишет виджет как обычно, значением:
   `Counter{Title: "…"}`.
3. **Параметры и состояние различаются по первой букве поля** — так в Go и так различают «внешнее» и «своё».
   Когда родитель перестраивается, в живой экземпляр переписываются только экспортируемые поля (параметры);
   неэкспортируемые (состояние) и сам `State` не трогаются.
4. **Методы — у указателя** (`func (c *Counter) Build`), иначе они меняли бы копию. Если метод жизненного
   цикла объявлен у значения, Hexago паникует с объяснением — молча терять изменения хуже.
5. **Жизненный цикл** (всё, кроме Build, — по желанию):
   - `Build(ctx)` — из чего виджет состоит;
   - `Init(ctx)` — виджет появился в дереве, один раз, до первого Build (initState);
   - `Update(ctx, old Counter)` — родитель перестроился и передал параметры; `old` — прежние (didUpdateWidget);
   - `DependenciesChanged(ctx)` — изменились данные предков, полученные через `DependOn` (didChangeDependencies);
   - `Dispose()` — виджет убран из дерева (dispose).
   Сигнатура `Update` проверяется при появлении виджета: ошибка в ней — паника с правильным вариантом.
6. **`SetState(fn)`** меняет состояние и перестраивает виджет в следующем кадре; `Context()`, `Mounted()` —
   как у Flutter. SetState после Dispose — паника.
7. Попутно: дерево строится в первом кадре, когда известен размер экрана, а не в `NewBinding` —
   раньше при старте всё дерево строилось дважды.

## Альтернативы

- Оставить два типа, как во Flutter: привычно, но многословно, и это не то, чего хочет автор.
- Состояние отдельной маленькой структурой внутри виджета (`widgets.Keep[counterState]`): явнее,
  но снова два типа и обращение к состоянию через лишний вызов.
- Параметры помечать тегом поля (`hexago:"param"`): лишний шум; правило первой буквы и так знакомо по Go.

## Последствия

- Копирование параметров идёт через reflect — по одному разу на перестройку виджета с состоянием, это дёшево.
- Поле с маленькой буквы, которое родитель задал в литерале, тоже станет начальным значением состояния
  (в тестах это удобно: так передаётся общий журнал вызовов), но при перестройке родителя обновляться не будет.
- Встроенные виджеты движка с состоянием (GestureDetector, анимации, прокрутка) строятся так же.
