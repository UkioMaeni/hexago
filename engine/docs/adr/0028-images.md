# ADR-0028: Картинки: Image, ассеты, сеть, кеш

- Статус: принято
- Дата: 2026-11-24

## Контекст

- Приложениям нужны картинки: логотипы и иконки из самого приложения, фотографии из сети и с устройства.
- У `gfx` было только `DrawImage`: билинейная выборка каждого пикселя на каждом кадре. Это медленно
  для прокрутки, а при сильном уменьшении фотография «рябит».
- Папка `assets/` создавалась `hexago create`, но в APK не попадала.

## Решение

1. **`gfx.Bitmap`** — картинка, готовая к рисованию: пиксели в формате холста. `NewBitmap` делают один раз
   (можно не в потоке интерфейса), `Canvas.DrawBitmap(b, src, dst, opacity)` рисует часть `src` в прямоугольник
   `dst`.
   - Без поворота картинка встаёт ровно по пикселям экрана. Под этот размер она один раз пересчитывается:
     уменьшение — усреднением по площади (с предумножением прозрачности, без тёмной каймы), увеличение —
     билинейно. Bitmap запоминает две последние копии.
   - Дальше картинка только копируется. Непрозрачная (фотография) — целыми строками.
   - С поворотом каждый пиксель берётся билинейно. При сильном уменьшении — из уменьшенной копии, чтобы
     не было ряби.
   - Выборка не выходит за кусок `src`: соседи в листе спрайтов не подтекают.
2. **`assets`** — новый пакет: файлы папки `assets/` проекта (`assets.Open`, `ReadFile`, `FS`).
   - На Android `app.Run` подключает файлы из APK. Java передаёт `AssetManager` в `nativeOnCreate`, Go читает
     через `AAssetManager` (`android.Assets()` — это `fs.FS`).
   - В тестах и на компьютере это папка `assets` в текущей папке; `SetFS` подменяет источник.
   - Шаблон `hexago create`: `assets.srcDir("../../assets")` в `build.gradle.kts`. `hexago run` подсказывает
     старым проектам, какой строки не хватает, но сам их файлы не правит.
3. **Источники картинок** (`painting.ImageProvider`: `Key`, `Load`) — `AssetImage`, `FileImage`, `MemoryImage`;
   свой источник — любой тип с этими методами. `painting.DecodeImage` понимает PNG, JPEG, GIF (первый кадр)
   и WebP. WebP берётся из `golang.org/x/image`, который уже есть в зависимостях.
4. **Картинки из сети** — отдельный пакет `netimage` (`netimage.Image{URL, Headers}`).
   - HTTP-клиент Go на Android весит много. Демо: 7,4 МБ без `net/http`, 10,9 МБ, если `painting` его только
     импортирует, 14,4 МБ с картинками из сети.
   - Отдельный пакет — платит только тот, кому сеть нужна.
   - Имена разрешает системный резолвер (Go на Android использует cgo), сертификаты берутся из системы.
   - В шаблон манифеста добавлено разрешение `INTERNET`. Оно обычное: пользователя не спрашивают.
5. **Кеш** (`painting.ResolveImage`, `CachedImage`, `EvictImage`, `ClearImageCache`, `SetImageCacheLimit`).
   - До 100 МБ пикселей; первыми вытесняются давно не нужные картинки.
   - Одну картинку, которую ждут несколько виджетов, грузят один раз.
   - Одновременно грузится не больше 6 картинок.
   - Ошибки не кешируются. Паника в чужом источнике становится ошибкой.
6. **Виджеты.**
   - `widgets.Image{Source, Width, Height, Fit, Alignment, Placeholder, Error}`. Картинка грузится в горутине.
   - Загруженная картинка показывается из кеша сразу, без пустого кадра.
   - Пока картинка грузится, на её месте `Placeholder` или пустое место размером `Width`×`Height`. Если
     не загрузилась — `Error` или пустое место, а ошибка уходит в лог.
   - Если источник сменили во время загрузки, опоздавшая картинка не показывается.
   - Один пиксель картинки — один dp, как у сетевых картинок во Flutter.
   - `widgets.RawImage` рисует готовый `gfx.Bitmap`.
   - `rendering.ImageBox` раскладывается как `RenderImage` (`Constraints.ConstrainAspect`).
   - `painting.BoxFit` (по умолчанию `ScaleDown`, как во Flutter), `FitSizes`, `Inscribe`.
7. **Возврат в поток интерфейса.** `Binding.Post` вызывают из любой горутины; `app.Run` подставляет
   `android.Post`. Без платформы функции копятся и выполняются в начале кадра — так работают тесты.

## Проверка

- Тесты:
  - `Bitmap`: форматы (NRGBA, RGBA с предумножением, YCbCr), точная копия, усреднение при уменьшении,
    отсутствие тёмной каймы, билинейное увеличение, прозрачность, обрезка, кусок картинки, хранение копий;
  - эталоны (проверены глазами): `bitmap_scaled` — уменьшение, увеличение куска, поворот, плотность 2;
    `image_fits` — все `BoxFit`, выравнивание, естественный размер, заглушка, ошибка;
  - источники: ассет, файл, память, сеть (локальный тестовый сервер, заголовки, 404, не картинка);
  - кеш: одна загрузка на нескольких ждущих, вытеснение старых, слишком большая картинка, ошибки
    не кешируются, паника источника;
  - виджет: размер во время загрузки, картинка из кеша в первом кадре, опоздавшая загрузка, ошибка;
  - подсказки `hexago run` старым проектам.
- Скорость (компьютер): копирование непрозрачной картинки на весь экран 1080×2400 — 6 мс; пересчёт
  фотографии 4000×3000 под 1080×810 — 12 мс (строки делятся между ядрами).
- Эмулятор (Android 16):
  - PNG с прозрачностью из APK на светлом и тёмном фоне;
  - JPEG 2400×1600 с `Cover`;
  - фотография по HTTPS, ошибка 404 текстом;
  - прокрутка экрана с картинками — 60 кадров в секунду.

## Альтернативы

- Декодировать картинки системой (`BitmapFactory` через JNI): быстрее для больших JPEG, понимает EXIF
  и HEIF. Но это путь только для Android, и пиксели всё равно пришлось бы копировать в Go. Декодеры Go
  работают везде и в тестах.
- Готовые фильтры `golang.org/x/image/draw` (CatmullRom): для фотографии в десятки раз медленнее, чем
  усреднение по площади. А именно уменьшение — главный случай.
- Оставить `NetworkImage` в `painting`, как во Flutter: каждое приложение платило бы за HTTP-клиент
  3,4 МБ, даже без картинок из сети.

## Последствия

- Первый показ большой фотографии стоит пересчёта под размер в потоке интерфейса (10–40 мс).
  Масштабирующая анимация картинки пересчитывает её на каждом кадре.
- Декодированная фотография держит в памяти все свои пиксели (12 Мп — 48 МБ). Уменьшения при
  декодировании (`cacheWidth` во Flutter) пока нет.
- Нет: варианты ассетов под плотность экрана (`2.0x/`), поворот JPEG по EXIF, анимированные GIF и WebP,
  кеш картинок из сети на диске.
- Картинка без поворота встаёт по целым пикселям экрана: при дробном сдвиге она может разойтись
  с соседним рисунком на полпикселя.
